# Operating Work Hub

## Deployment boundary

One Node 24 process serves the API, browser assets and durable outbox worker. SQLite
and the simulator's independent persistent ledger live under `DATA_DIR` (default
`./data`). No Docker daemon, runtime binary, provider account, model API key, external
database or scheduler is needed. The current connector installations are simulations.

The default bind address is `127.0.0.1`. For network use, put the application behind
an authenticated TLS reverse proxy and set `PUBLIC_ORIGIN=https://your-hub.example`
and `HOST=0.0.0.0`. The service refuses non-loopback configuration without an HTTPS
public origin. Do not expose the direct cleartext Node listener on an untrusted
network. Forward the original Host/Origin unchanged; cookies use Secure with HTTPS.

Administrator credentials are generated by a local CLI and shown once. Keep them in
a password manager. Login exchanges a token for an expiring HttpOnly SameSite cookie;
reusable tokens are never saved in browser storage. The authentication database holds
hashes, not plaintext credentials. Runtime credentials are a different principal
class, bound to one task/session/attempt/generation and an explicit operation list.

## Backup and restore

1. Stop the hub service gracefully. This does **not** stop any external runtime or
   destroy an environment. Never copy only the main SQLite file from a live WAL DB.
2. Back up the entire `DATA_DIR`, including authentication, hub and simulator ledger
   SQLite files and any `-wal`/`-shm` files that remain. Preserve filesystem permissions.
3. Secure the backup as private application data. Tokens are hashed, but work text
   and stored outputs can contain secrets users pasted themselves. A JSON export is
   a portable work-record export, **not** an authentication or full recovery backup.
4. To restore, stop the destination service, restore the whole directory and use
   the same configuration and connector installations. Start in reconciliation mode:
   existing operation IDs are looked up, not issued as fresh effects. Do not merge
   a simulator ledger from a different backup or discard the old operation ledger.
5. Inspect unknown operations, missing identities, pending deliveries and active
   attempts before authorizing new work. Restoring local data cannot prove that an
   external process stopped while the service was offline.

Back up externally managed credential-reference configuration independently. No
production connector or external secret resolver is supplied in this phase.

## Recovery rules

An unknown side effect is not a failed effect and not permission to retry. Inspect
or reconcile the original operation ID. Preserve its task/session/work-area reservation
until actual termination, fencing, or an explicit audited operator decision. Never
replace a resource merely because its locator or friendly name is reusable.

Responses are immutable human decisions. An unknown delivery does not require the
user to answer again. Acknowledgment is separate from runtime-action success.
Closing a tab or restarting the hub changes neither work nor infrastructure lifecycle.

## Capacity claims

The v0.3 target envelope is 10,000 tasks, 20 simulated sessions and 100 small events/s
on a documented equivalent of 4 vCPU/8 GiB. These are test targets, not measured
production claims. Consult the final verification report for actual measurements.

## Diagnostics and privacy

The product exposes canonical receipts and operation uncertainty; structured service
logs carry identifiers, not task prompts, answer text, bearer tokens or provider
secrets. Do not paste tokens into task text. Exports exclude authentication material,
private locators and live route handles. Output retention creates explicit history
gaps and never deletes canonical questions, answers or result summaries.
